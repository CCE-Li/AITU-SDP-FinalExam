1. Introduction

1.1 Background and motivation

A design pattern is a reusable solution to a problem that appears again and again in software design. Patterns are not libraries and they cannot be copied into a project as code; they are descriptions of how responsibilities should be distributed between classes. The value of a pattern only becomes visible when several of them have to work inside one program, because that is the moment when the boundaries between them must be decided.

For this project the domain of a restaurant ordering system was chosen. The domain is small enough to be understood in a few minutes, but it contains several independent reasons to change: the menu grows, meals are assembled from parts, customers receive different discounts, food is served in different channels, and a single checkout touches stock, money and the kitchen. Each of these concerns is isolated behind its own pattern, which makes the system a good demonstration of coordinated pattern usage rather than seven unrelated examples.

1.2 Objectives of the project

The project pursues four objectives:

  1. Implement at least six design patterns from the course in a single Java application. This implementation contains seven: Factory Method, Builder, Abstract Factory, Bridge, Facade, Strategy and Visitor.
  2. Make the patterns cooperate inside one ordering workflow, so that the result is an application and not a collection of demos.
  3. Keep the code short and readable: no framework, no database, no external library, only the JDK.
  4. Produce the artefacts required for the defence: UML diagrams, screenshots of the running program and this report.

The scope deliberately excludes persistence and networking. Adding them would not demonstrate any additional design pattern and would hide the pattern structure behind infrastructure code. Section 4 explains how they could be added later.

1.4 Structure of this report

Section 2 is the body of the report. It starts with the architecture of the system (2.1), then presents the seven patterns in the order in which an order is processed: creation of dishes (2.2–2.4), serving (2.5), checkout (2.6–2.7) and reporting (2.8). Section 2.9 explains how the patterns collaborate and maps them to the project requirements; 2.10 contains the screenshots and 2.11 verifies the numerical results. Section 3 concludes the report, Section 4 lists further work, and the appendices contain the complete class diagram, the full source code and the build instructions.
